# Servio Ride Engine — Technical Integration Report

Prepared before any code changes, per the surgical-integration spec (section 29). This report reflects a direct inspection of the Servio repository at `C:\Users\Israel\Desktop\servio` and both reference repositories, not assumptions.

## 1. What Servio actually is

Servio is a customized deployment of the **Sharetribe Web Template** — the open-source frontend (`sharetribe-flex-sdk` ^1.24.2) that pairs with **Sharetribe Flex**, a hosted marketplace backend-as-a-service. The app is a React 17 single-page app rendered through a custom Express 5 server (`server/index.js`, `server/renderer.js`) for SSR, with React Router 5 for routing. `package.json` names the project `servio`, and `render.yaml` shows it deploys to Render. Servio has already been meaningfully customized on top of the stock template: 20 local-service categories (`src/config/configServiceCategories.js`), service-area configuration (`configServiceAreas.js`), and its own branding layer — this is not a bare Sharetribe demo.

The single most important architectural fact for this project: **Sharetribe Flex, not this repository, is the system of record.** Users, listings, transactions, messages, reviews, and payments all live in Sharetribe's hosted Marketplace API. This repo contains no database of its own — no Postgres, no Mongo, nothing. Every "backend change" the spec asks for has to be understood as either (a) configuration inside the hosted Sharetribe Console, (b) a new Sharetribe transaction process (a state machine definition that Sharetribe itself executes), (c) extended-data fields attached to Sharetribe's existing entities, or (d) logic inside this repo's thin Node server, which only ever acts as a trusted intermediary calling the Sharetribe API — it cannot maintain its own persistent state beyond what it asks Sharetribe to store. This changes what several items in the spec (a standalone `DriverLocation` table, arbitrary custom entities, etc.) have to become in practice, covered in section 5.

## 2. Authentication

Identity is entirely owned by Sharetribe. There is no local user table. Login/signup, password auth, and IdP login (Google/Facebook, wired in `server/api/auth/google.js`, `facebook.js`, `createUserWithIdp.js`, `loginWithIdp.js`) all go through the Sharetribe Marketplace API; the Express server only brokers cookies/tokens (`server/api-util/cookieOptions.js`, `idToken.js`). A "provider" is not a separate account type — it is a Sharetribe user who has published one or more listings. This is good news for the spec's rule against a second identity system: there is nothing to bypass, because Firebase auth was never introduced here, and a Servio user can already be a customer and a service provider on the same account. Ride will map onto exactly this model — a driver is a Sharetribe user with a "Ride" listing, not a new account type.

## 3. Mapbox

Already fully wired and reusable. `src/config/configMaps.js` is the central toggle between Mapbox and Google; `src/components/Map/` contains `MapboxMap.js`, `DynamicMapboxMap.js`, `StaticMapboxMap.js`; `GeocoderMapbox.js` under `LocationAutocompleteInput` handles address autocomplete; `SearchMapWithMapbox.js` drives the search-page map. The token is read from `REACT_APP_MAPBOX_ACCESS_TOKEN`, and — notably — `@mapbox/polyline` is already a dependency, meaning route-polyline decoding is a solved problem here already. There is no token value in the repo (only the empty key name in `.env.example`), so the live token exists only in the actual deployment environment (Render), which I cannot see from here. Ride will extend `Map.js`/`MapboxMap.js` with new marker types (vehicle, pickup, destination) and a route layer, rather than introducing any new Mapbox client or a second token.

## 4. Payments

Also already fully owned by Sharetribe, and this is the second piece of very good news: Sharetribe's Stripe Connect integration means Servio never had to write its own charge/payout code. `server/api/transaction-line-items.js` and `server/api-util/lineItems.js` compute line items server-side from a listing and order data; `server/api-util/sdk.js` exposes `fetchCommission(sdk)`, which pulls provider/customer commission rates from a Console-managed JSON asset — so commission is already configurable without a redeploy, exactly what the spec asks for. `server/api/transition-privileged.js` is the sanctioned extension point: a privileged transition runs trusted Node code (this file) before Sharetribe commits a state transition, which is where fare validation, driver-assignment enforcement, and "don't trust the client" checks belong. Ride payments will be a new transaction type flowing through this same pipeline (new line items, same commission asset, same Stripe Connect payout), not a parallel payment system.

## 5. The real constraint: Sharetribe has no generic custom database

The spec's suggested entities (`Ride`, `DriverAvailability`, `DriverLocation`, `RidePricing`, `RideEvent`) assume a backend where you can add arbitrary tables. Sharetribe doesn't offer that. What it offers instead:

- A **new transaction process** (an EDN state machine, following the pattern already in `ext/transaction-processes/default-booking/process.edn` etc.) becomes the `Ride` entity and its state machine simultaneously — Sharetribe transitions map directly onto the REQUESTED → DRIVER_ASSIGNED → ... → COMPLETED states the spec asks for, and Sharetribe enforces valid-transition rules natively (you cannot invent a transition that isn't in the graph, which satisfies section 9's "invalid transitions must be rejected").
- `DriverAvailability` becomes a public/private data field on the driver's user profile or Ride listing (e.g. `privateData.isOnline`), updated through a normal Sharetribe API call guarded by our own server route.
- `RidePricing` becomes a Console-managed JSON asset, fetched the same way `fetchCommission` already is — configurable without a redeploy, per section 14.
- `RideEvent` (audit trail) becomes the transaction's own transition history, which Sharetribe already stores and timestamps for free.
- `DriverLocation` is the one genuine gap. Sharetribe's extended data is versioned key/value storage meant for occasional writes, not a high-frequency time-series feed — writing to it every couple of seconds per active driver is the wrong tool and will hit rate limits under real load. The realistic, still-fully-real approach is to store only the *current* location (overwriting, not appending) on the transaction's `protectedData`, updated on a throttled interval (roughly 5–15 seconds, adaptive to whether a trip is active), with the rider polling the same field on a matching interval. This is genuinely live tracking — just interval-based rather than sub-second push — and it keeps everything inside Servio's existing Sharetribe foundation instead of introducing a second realtime backend (which the spec explicitly forbids). I flag this now because it's a real trade-off, not an implementation detail to gloss over: true sub-second push tracking would require an external realtime channel that the spec's own rules rule out.

## 6. Categories and listing types — a second external-system dependency

`src/config/configServiceCategories.js` is explicitly documented in-file as a marketing/SEO layer only, powering the `/services/:categorySlug` landing pages. The categories that listings are actually filterable by live in **Sharetribe Console** (Build → Content → Categories), and `sharetribe-setup/categories.json` mirrors that Console-side list for setup via the Sharetribe CLI (`flex-cli`). Adding "Ride" as a real, searchable category — and adding the new transaction process from section 5 — both require pushing configuration to Sharetribe's hosted Console, which is an external system outside this repository. I found no `flex-cli` installed in this environment and no populated `.env` (only `.env.example`/`.env-template`/`.env.development`, all placeholders) — meaning I currently have no Sharetribe API credentials, no Mapbox token, and no Stripe keys available to me. I can write every file needed (the new category JSON, the new process EDN, its email templates) but cannot push them to Sharetribe's Console myself without credentials only you hold.

## 7. Notifications

Sharetribe's own transactional email system handles this today — each transition in `ext/transaction-processes/*/process.edn` fires an HTML/subject template pair (see the `default-booking` templates for the pattern), deployed to Console the same way as the process itself. I found no separate push/SMS provider wired into this repo. Ride notifications (driver found, driver arriving, trip started, etc., per section 18 of the spec) will follow the same template pattern as a natural part of the new Ride process, rather than a new notification system.

## 8. Reference repositories — confirmed as concept references only, per your own instruction

Both `UberClone` (rider) and `UberClone_DriverApp` (driver) are **Flutter native-mobile apps**, not web apps. Their `pubspec.yaml` depends on `firebase_auth`, `firebase_core`, and `firebase_database` (Firebase Realtime Database is how they sync trip state and driver location), plus a custom fork of `flutter_mapbox_navigation` on the driver side for turn-by-turn. Neither shares a language, framework, database, or deployment model with Servio. This confirms the spec's own caution was correct: there is nothing architectural to port from these repos. What is genuinely useful is their screen/flow structure — `cab_screen.dart` + `waiting_bottom_sheet.dart` + `trip_accepted_bottom_sheet.dart` on the rider side, and `driver_availability_container.dart` + `available_trips_container.dart` + `trip_details_dialog.dart` on the driver side — as a reference for sequencing the Servio Ride UI (map-first screen, bottom-sheet controls, a driver-card once matched), which I'll rebuild natively in Servio's own React component system and CSS module conventions, not copied.

## 9. One open product question the spec doesn't resolve

Servio is a web app. The spec's driver-side requirements (background location while the app is minimized, battery-aware tracking intervals, "the driver must never receive requests while offline" enforced at the OS/app level) describe native mobile app behavior. A browser tab cannot reliably report location once backgrounded or the screen locks — that's a browser/OS limitation, not something any amount of engineering effort in this repo works around. Before Phase 1 I need to know whether the driver experience should be (a) a responsive web experience inside Servio itself (Geolocation API, foreground-only, with honest "you've gone offline" states when the tab isn't active — no fake background tracking), or (b) a separate native app down the line. I've asked this below rather than guessing, since it changes what "real" driver tracking can honestly mean here.

## 10. Proposed phased plan

Given the two external dependencies above (Sharetribe Console/CLI access, and the driver-platform decision), the realistic build order is:

1. **Foundation (no Console access needed):** ride pricing config module (base fare, per-mile, per-minute, minimum, cancellation fee — Console-asset-backed like commission already is, with a local fallback default so it's testable before the asset exists), the Ride extended-data schema (what goes on the user, the listing, and the transaction), the map UI additions (pickup/destination/vehicle markers, route line) built on the existing `Map`/`MapboxMap` components, and the rider-side request flow UI wired to real geocoding via the existing `GeocoderMapbox`.
2. **Process design:** draft the new `ride` transaction process EDN (states per section 9 of the spec) plus its email templates, following the exact pattern of `ext/transaction-processes/default-booking`, ready to push.
3. **Console setup (needs your access or credentials):** push the new category, listing type, and transaction process to Sharetribe Console via `flex-cli`; configure the ride-pricing and commission assets.
4. **Server-side enforcement:** privileged-transition logic for fare validation, single-acceptance enforcement, and nearest-eligible-driver matching, added to `transition-privileged.js` alongside the existing negotiation logic.
5. **Live state:** driver online/offline + location polling, trip state UI, dispatch flow, ratings, history integration, admin views.
6. **Hardening:** the failure-mode matrix in section 23 of the spec (no drivers found, payment failure, stale location, dropped connection, duplicate acceptance, etc.), then end-to-end testing per section 27.

I'd like your direction on the four points below before starting Phase 1 code, since two of them (Console access, driver platform) determine what Phase 1 can actually connect to.
